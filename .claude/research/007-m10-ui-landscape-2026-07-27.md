# M10 UI Landscape — Frontend Reuse & Form Factor

**Date**: 2026-07-27
**Context**: M10 (Interactive CLI/UI) replaces axiom's one-shot argparse CLI with a real, shippable interface. Kaushik rejected a TUI as "not impressive" and wants something competitive with commercial agent products. Two questions: (1) adapt an existing open-source chat UI as axiom's frontend, or build custom — per this project's "reuse before build" rule; (2) what form factor — self-hosted web app, desktop app (Electron/Tauri), or other.
**Status**: Research complete

---

## Evaluation criteria

Derived from axiom's actual, already-built architecture (not aspirational):

1. **Streaming responses** — token-by-token, not block-at-completion.
2. **Blocking human-in-the-loop tool approval** — the M4 Guardrails GATE must pause mid-turn and get a real approve/deny from the user for a specific destructive tool call, then resume. This is the hardest requirement — most chat UIs assume a backend that runs to completion or streams to completion, not one that blocks mid-response waiting on a human.
3. **Observability/trace view** — axiom's M2 already emits a JSONL phase-span trace (perceive/reason/act/observe, timing, metadata); the UI should be able to render something like it, ideally natively.
4. **Multi-provider switching** — claude / local / committee, selectable in-session (M6/M7).
5. **Single-user, persona-driven** — not multi-tenant SaaS; no need for accounts/orgs/billing that most of these projects carry as baggage.
6. **Python-native fit** — axiom's core is a custom Python PRAO loop, not LangChain/LlamaIndex; a candidate that forces the control loop through a non-Python runtime is architecturally awkward.

---

## Part 1 — Build vs. reuse: existing OSS chat/agent UIs

Methodology: license, star count, and commit-recency figures pulled live from the GitHub API on 2026-07-27; architecture/feature claims from primary docs or GitHub issues/discussions, cited per claim.

### Chainlit (Chainlit/chainlit)

- **License**: Apache-2.0.
- **Activity**: 12,338 stars, 1,727 forks, ~196 contributors, 136 open issues. Last commit 2026-05-26 (~9 weeks before research date), 68 commits in the trailing 6 months — healthy but visibly slower cadence than the other candidates below. Latest release 2.11.1 (2026-04-22).
- **Backend architecture**: A FastAPI + Socket.IO server *is* the backend — Python decorators (`@cl.on_chat_start`, `@cl.on_message`) wrap your own logic directly. "Compatible with all Python programs and libraries"; LangChain/LlamaIndex are optional, not required. Of everything researched, this is the most direct architectural fit for a bespoke Python PRAO loop — no cross-language boundary, no OpenAI-compatible SSE shim needed in front of the backend.
- **Blocking approval — native and exact match**: `await cl.AskActionMessage(...).send()` genuinely suspends the Python coroutine handling the turn until the user clicks approve/deny (default 90s timeout, configurable), returning an `AskActionResponse`. ([docs](https://docs.chainlit.io/api-reference/ask/ask-for-action))
- **Trace view — native and closest match to axiom's own concept**: a `Step` concept (`@cl.step` decorator / `cl.Step` context manager) renders a nested chain-of-thought tree with input/output per step, toggleable via `config.ui.cot`. Each Step has start/end semantics a perceive/reason/act/observe wrapper could populate directly. ([docs](https://docs.chainlit.io/concepts/step))
- **Multi-provider switching**: `ChatProfile` (profile switcher dropdown) + `ChatSettings` (a `Select` widget) — light-effort fit for claude/local/committee.
- **Effort estimate**: Light–medium. All four hard requirements have a direct, documented, native primitive — configuration/wiring, not forking.

**Deep-dive follow-up (2026-07-27), triggered by Kaushik's questions on customization depth, the no-session/voice-assistant paradigm, and canvas:**
- **Customization ceiling**: real but bounded by default — `custom_css`/`custom_js` injection, theming (colors, logo, avatars, layout), plus a `custom_build` escape hatch to swap in an entirely custom frontend production build that still talks to Chainlit's backend via `@chainlit/react-client`. Reaching Claude-Code-level bespoke polish means using that escape hatch — i.e. writing your own frontend — not configuring the default one. ([docs.chainlit.io/backend/config/ui](https://docs.chainlit.io/backend/config/ui))
- **Session/thread paradigm — a real mismatch with axiom's actual vision**: Chainlit's default UI is a thread/session-list app (same shape as ChatGPT's sidebar of past conversations). The UI config docs have **no documented option to disable or hide the chat-history sidebar** — it's assumed, not optional. Axiom's actual target (one persistent assistant, memory-driven recall rather than a browsable session list) doesn't fit this shape without going through the same `custom_build` escape hatch as the customization question above.
- **Voice — a genuine, concretely-verified strength**: native `@cl.on_audio_chunk` mic access, plus a documented **OpenAI Realtime API example** for low-latency two-way voice conversation — the same shape as ChatGPT voice mode, and confirmed via docs, not just claimed. ([docs.chainlit.io/advanced-features/multi-modal](https://docs.chainlit.io/advanced-features/multi-modal))
- **Canvas — confirmed absent, deliberately.** [GitHub Issue #2104](https://github.com/Chainlit/chainlit/issues/2104), "Is there any plan for artifact support in chainlit?", is **closed as not planned**. What exists instead is `CustomElement` — author a `.jsx` widget, shown inline/side/page — good for a visualization or interactive card, not an editable live-preview document surface like Claude Artifacts or ChatGPT Canvas. ([docs.chainlit.io/api-reference/elements/custom](https://docs.chainlit.io/api-reference/elements/custom))
- **Net**: the original "light–medium effort" estimate holds for a *standard chat-UI* shape. For axiom's actual vision (voice-first, no session list, memory-driven, possibly wanting canvas later), the real cost converges on the same `custom_build`-a-custom-frontend path either way — which changes the effort comparison against CopilotKit below.

### AnythingLLM (Mintplex-Labs/anything-llm)

- **License**: MIT.
- **Activity**: 63,957 stars, 7,010 forks, ~212 contributors, 336 open issues, last push 2026-07-25.
- **Backend architecture**: Full REST API; "Generic OpenAI" provider for pointing at any OpenAI-compatible backend by base URL. Custom **agent skills**, however, are Node.js modules (`handler.js` + `plugin.json`) hot-loaded into AnythingLLM's own Node agent runtime — not remote Python code.
- **Blocking approval — native, strong**: `await this.requestToolApproval({ payload, description })` pauses the agent and shows the same Approve/Reject card used by AnythingLLM's own built-in destructive tools (e.g. Gmail send). ([handler.js reference](https://docs.anythingllm.com/agent/custom/handler-js))
- **Limitation found**: a custom skill's `handler` must return a single complete string at the end — "anything else may break the agent invocation or loop indefinitely." So an agent-skill turn's *final* answer is not token-streamed, only `introspect()` progress lines are live. Partially conflicts with requirement #1 specifically for tool-invoking turns.
- **Trace view**: `introspect()` streams real-time thought/observation lines, but no structured span/timing trace — would need custom rendering, and loses timing as a first-class element.
- **Architectural friction**: axiom's Python PRAO loop would need to either become a thin Node shim calling back into a Python HTTP service per phase, or run as one "mega-skill" doing a single blocking HTTP call per turn — inverts control (Node drives, Python serves), awkward for a project whose core value is its own control loop.
- **Effort estimate**: Medium. Best-in-class approval/live-reasoning primitives, but a real cross-language integration cost.

### Open WebUI (open-webui/open-webui)

- **License**: Custom "Open WebUI License" (BSD-3-style) — branding-retention clause, waived for deployments ≤50 users/30 days (axiom qualifies as single-user), but not unrestricted OSS. ([LICENSE](https://github.com/open-webui/open-webui/blob/main/LICENSE))
- **Activity**: 146,918 stars, 21,352 forks, ~391 contributors, 268 open issues, last push same day as research (2026-07-27) — by far the largest community of any candidate.
- **Backend architecture**: Expects an OpenAI-compatible `/v1/chat/completions` SSE endpoint or Ollama's API. Custom logic goes through a separate **Pipelines** framework — a UI-agnostic plugin server you run alongside it.
- **Blocking approval — real but semi-hidden**: a documented `__event_call__` primitive with a `"confirmation"` event type that a Python Tool can `await` to block mid-turn for approve/deny. A first-class *built-in-tool* approval UI was proposed and rejected from core (PRs closed for merge conflicts / missing auth / no timeout handling) — a maintainer confirmed the primitive works for custom tools today, just isn't polished for arbitrary built-ins. ([Discussion #16701](https://github.com/open-webui/open-webui/discussions/16701))
- **Trace view**: none built-in; a "status" event type shows progress text next to tool calls, but nothing resembling a phase-span timeline.
- **Effort estimate**: Medium. Requires building an OpenAI-compatible SSE proxy in front of axiom's PRAO loop plus a Pipelines/Tool wrapper for the approval interrupt.

### LibreChat (danny-avila/LibreChat)

- **License**: MIT.
- **Activity**: 41,328 stars, 8,511 forks, ~379 contributors, 631 open issues, last push same day as research.
- **Backend architecture**: "Custom Endpoints" expect an OpenAI-compatible SSE service, plus a native `provider: "anthropic"` mode.
- **Blocking approval — not implemented**: an open, unassigned backlog item ([Issue #5580](https://github.com/danny-avila/LibreChat/issues/5580)), explicitly citing Claude Desktop's approval UX as the model to copy, listed on the [2026 roadmap](https://www.librechat.ai/blog/2026-02-18_2026_roadmap) but with no linked PR/branch/design. Unlike Open WebUI, there is no existing low-level hook — you'd be adding the interrupt/resume mechanism to their agent-execution loop yourself.
- **Effort estimate**: Medium–heavy. Streaming and provider-switching are easy; the one requirement that matters most has no hook point.

### Lobe Chat (lobehub/lobe-chat)

- **License**: LobeHub Community License (Apache-2.0-based) — free to run/host, but **a commercial license is required to distribute a derivative fork**. A real constraint if axiom's UI work is ever forked/redistributed. ([LICENSE](https://github.com/lobehub/lobe-chat/blob/main/LICENSE))
- **Activity**: 80,871 stars, 15,715 forks, ~341 contributors, last push same day as research.
- **Backend architecture**: A separate **Plugin Gateway** service routes function-calling requests to plugin implementations described by an OpenAPI-like manifest; also supports MCP servers directly.
- **Blocking approval**: not found/confirmed — the plugin flow (fetch manifest → call gateway → execute → write result into the stream) reads as auto-execute, not pause-for-approval. Flagged as an unconfirmed gap, not asserted as absent.
- **Effort estimate**: Heavy. Largest integration surface (TS/Next.js monolith + separate gateway service), a real license caveat, and no evidence of the one primitive that matters most.

### CopilotKit + AG-UI protocol — deep dive (2026-07-27 follow-up)

Initially logged as an "adjacent/specialized" toolkit rather than a full candidate; a follow-up pass (triggered by Kaushik's questions on customization depth, the no-session/voice-assistant paradigm, and canvas) went deeper specifically on Python-friendliness, maturity, canvas, and HITL for a custom (non-LangGraph) agent loop — the axiom-relevant case.

**Company/maturity**: CopilotKit raised a **$27M Series A** (May 2026, led by Glilot Capital Partners, NFX, SignalFire), independently reported by [TechCrunch](https://techcrunch.com/2026/05/05/copilotkit-raises-27m-to-help-devs-deploy-app-native-ai-agents/), [Pulse2](https://pulse2.com/copilotkit-27-million-series-a-raised-for-enterprise-agentic-frontend-stack/), and [ynetnews](https://www.ynetnews.com/business/article/rkvnzrv0bx). Production deployments cited include DocuSign, S&P Global, Cisco, Deutsche Telekom, Function Health (company-sourced claim of "majority of Fortune 500," corroborated across three independent outlets for the funding round itself, not independently verified for the Fortune-500 claim specifically). GitHub: [CopilotKit](https://github.com/copilotkit/copilotkit) 36,316★ MIT, [AG-UI](https://github.com/ag-ui-protocol/ag-ui) 14,926★ MIT, both with commits the same day as this research — actively developed, not a side project.

**Python-friendliness — two real integration levels, not one:**
1. **High-level**: the official `copilotkit` PyPI package (v0.1.94, released 2026-06-04, Python ≥3.10 <3.15) ships `CopilotKitRemoteEndpoint` + `Action` + `add_fastapi_endpoint`. Verified via a working code sample ([dev.to guide](https://dev.to/copilotkit/build-a-frontend-for-your-microsoft-agent-framework-python-agents-with-ag-ui-4ghk)) that **LangGraph is optional, not required** for this "Direct-to-LLM" pattern — a plain async Python function wrapped in `CopilotAction` and registered on `CopilotKitRemoteEndpoint` is sufficient; LangGraph only enters for an explicitly optional "Dynamic Agents" extension. (Correction against this package's own PyPI description, which frames it as LangGraph/LangChain-first — the dev.to code sample demonstrates the LangGraph-free path works today regardless of how the package markets itself.)
2. **Low-level**: the separate `ag-ui-protocol` PyPI package is a framework-agnostic, Pydantic-based protocol/event-encoding library (`ag_ui.core` for types/events, `ag_ui.encoder` for SSE formatting, 16 core event types, automatic camelCase conversion for the frontend) — no LangGraph/CrewAI dependency at all. This is the layer axiom would actually integrate against: hand-emit AG-UI events from the PRAO loop's own perceive/reason/act/observe phases, with full control, same as how the M2 observability trace is already hand-emitted today.

**Real precedent for a custom (non-LangGraph) agent loop**: CopilotKit documents a working **Pydantic AI** integration ([docs.showcase.copilotkit.ai/pydantic-ai](https://docs.showcase.copilotkit.ai/pydantic-ai/human-in-the-loop/agent)) — Pydantic AI is architecturally the closest public analog to axiom's own custom PRAO loop (a bespoke Python agent framework, not LangGraph). Its `pydantic_ai.Agent` with plain `@agent.tool_plain` functions integrates via `CopilotKitState`, and HITL works by the frontend registering a `useFrontendTool` (or `useCopilotAction`) with `renderAndWaitForResponse` matching the backend tool's name — when the agent calls that tool, control transfers to the frontend, the user approves/rejects, and the response flows back into the agent loop. This is a **name-matching convention**, not automatic framework magic — confirmed by a parallel finding ([GitHub Issue #2770](https://github.com/CopilotKit/CopilotKit/issues/2770)): automatic interrupt-detection currently only exists for Microsoft's Agent Framework (`ApprovalRequiredAIFunction`); every other backend, including Pydantic AI's, wires HITL manually by name. Axiom would be in the same "manual but working" bucket — a real, documented, production-referenced pattern, just not a one-line auto-detect.

**Canvas — the actual thing, unlike Chainlit.** CopilotKit's "Generative UI" ships a **"Chat+" surface**: a side-by-side/multi-pane layout, chat in one pane, "a dynamic canvas in another... a shared working space where agent-generated UI appears and evolves," explicitly positioned as backend-agnostic ("CopilotKit works with any generative UI," AG-UI as "a universal runtime"). ([copilotkit.ai/generative-ui](https://www.copilotkit.ai/generative-ui)) This is architecturally the Claude-Artifacts/ChatGPT-Canvas pattern Chainlit's maintainers explicitly closed as not-planned — full editable/live-preview interactivity of the canvas pane wasn't confirmed to the same code-sample depth as the HITL pattern above, but the surface itself is a first-party, documented feature, not a community request.

**Voice**: documented as shipping "across the stack including voice agents" alongside React/Vue/Slack/Teams/Discord, but not verified to the same code-level depth as Chainlit's concrete `on_audio_chunk`/OpenAI-Realtime-API example — flagged here as claimed-and-plausible given the company's scale, not independently confirmed with a working sample the way Chainlit's voice path was.

**The structural point that actually resolves Kaushik's Q2 (no chat-sessions, single persistent assistant)**: CopilotKit is fundamentally a different kind of product than Chainlit. Chainlit ships a *complete pre-built app* (you configure/theme/escape-hatch out of it); CopilotKit ships *React hooks and components* (`useCopilotAction`, `useFrontendTool`, generative-UI components) that you compose into your own app shell from scratch. There is no default thread-list/session-switcher to fight or hide — you simply never build one. Chainlit's docs confirmed no supported way to disable its session sidebar; CopilotKit has no session sidebar to begin with unless you build one. This means the "no sessions, memory-driven not thread-driven" vision is *native* to CopilotKit's shape, not a workaround — the opposite of the Chainlit finding. The real cost is that axiom would be writing the entire frontend shell (chat pane, canvas pane, voice control, approval UI) in React/Next.js from square one — CopilotKit gives you the hard, agent-specific primitives (streaming, HITL, generative UI, canvas), not a finished app.

- **LangChain's Agent Chat UI** ([repo](https://github.com/langchain-ai/agent-chat-ui): 3,017★, MIT) — still explicitly out of scope: its interrupt/resume UI is wired to LangGraph's checkpointer semantics specifically, which axiom doesn't use and won't adopt.

No other actively-maintained, non-framework-coupled "approval-first" chat UI surfaced.

## Part 2 — Form factor: web app vs. desktop app

### Self-hosted web app (FastAPI/Python backend + browser frontend)

Real precedent: **Open WebUI** itself (FastAPI + Svelte, Docker or native install, 146k★) is the closest existing analog to what axiom would ship — proof this path can feel commercial-grade. **Jupyter** is the canonical "local web app" case (Tornado/ZeroMQ server on `127.0.0.1`), showing both that the model works and that "browser tab" is a real UX ceiling unless layered further. ([Jupyter docs](https://jupyter-notebook.readthedocs.io/en/4.x/public_server.html))

Lowest dev effort of any option for a Python-first team — no second language, no code-signing pipeline, no OS-specific packaging. Every other option below still needs this same web frontend; they just add a wrapper around it.

Ways to push past "just a tab":
- **PWA install** on Windows (Edge/Chrome) gives its own window, taskbar pin, Start-menu entry, Alt-Tab presence. ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/ux))
- **`pystray` systray launcher** (~50 lines) to start/stop the backend and open the window — gives the "always-available background agent" feel a one-shot CLI can't. ([pystray](https://pypi.org/project/pystray/))
- Real limits: PWA background execution is throttled, service workers get killed when idle, no true native systray/hardware access from the PWA itself. ([love2dev.com](https://love2dev.com/pwa/progressive-web-app-disadvantages/))

### Electron

Still what most commercial agent products actually ship: **Claude Desktop** ([confirmed](https://www.dbreunig.com/2026/02/21/why-is-claude-an-electron-app.html) — Anthropic's Boris Cherney cited engineer familiarity and web/desktop code-sharing as the reasons, not a capability gap), **ChatGPT Desktop on Windows** ("just an Electron-based Chrome wrapper" per reviewers), **Cursor** and **Windsurf** (both Electron/VS Code forks), **LM Studio** (Electron; ~200–500MB baseline RAM before any model loads, per its own bug tracker).

Real cost, from teams that shipped it: a solo indie dev's 25-release retrospective called auto-update "one of the highest-ROI infra decisions" but found code signing "complex and fragile"; auto-update requires standing up and maintaining an update-metadata server. ([DEV.to](https://dev.to/ryuji_saas/lessons-from-building-electron-auto-update-across-25-releases-1ah7)) Bundle size: ~150MB on disk for a "Hello World" app (bundled Chromium + Node per app). ([DoltHub](https://www.dolthub.com/blog/2025-11-13-electron-vs-tauri/))

### Tauri

Materially more mature than a year ago — Tauri 2.0 (stable late 2024) added mobile support, rewrote IPC for raw-payload speed, and added an externally-audited permissions/capabilities security model. ([Tauri 2.0 blog](https://v2.tauri.app/blog/tauri-20/)) Uses the OS's native webview (WebView2 on Windows — **preinstalled on Windows 11**, relevant since Kaushik is on Win 11) instead of bundling Chromium.

Real migration data: **Fluxzy** (Electron since Feb 2023 → Tauri v2 by Dec 2025) — Windows installer 190MB → 55MB, memory down across all OSes, faster cold start; real pain points were an Electron/Tauri auto-updater incompatibility (needed a bridge release), a two-pass Windows code-signing process, and Wayland GPU workarounds. Their migration succeeded specifically because the app already cleanly separated renderer/main-process/backend logic. ([Fluxzy writeup](https://www.fluxzy.io/resources/blogs/electron-to-tauri-migration-fluxzy-desktop)) **DoltHub** evaluated and stayed on Electron, citing no native `.appx`/`.msix` on Windows and macOS codesigning issues as blockers for their case. ([DoltHub](https://www.dolthub.com/blog/2025-11-13-electron-vs-tauri/))

**Directly applicable to axiom**: Tauri's **sidecar** mechanism bundles an external binary (e.g. a PyInstaller-frozen FastAPI server) alongside the Rust shell, communicating over local HTTP as a separate process. This is a documented, working pattern for exactly axiom's Python-backend shape. ([Tauri sidecar docs](https://v2.tauri.app/develop/sidecar/))

**Jan.ai** is built on Tauri specifically for the performance win over Electron, and is a closer scope-match to axiom (small, focused, single-purpose local AI tool) than Claude/Cursor/ChatGPT are. ([itsfoss.com](https://itsfoss.com/jan-ai/)) **Ollama Desktop** goes further still — a fully native Go app (not a web wrapper), confirming a lean-footprint precedent exists at the far end of this spectrum too. ([DeepWiki](https://deepwiki.com/ollama/ollama/8-development-guide))

### Middle ground: PyWebView

A lightweight, pure-Python webview wrapper (WinForms on Windows) with a built-in HTTP server, native menus/dialogs, and a two-way JS↔Python bridge — no Chromium bundling, no Rust toolchain. The best "stay pure-Python" middle ground between a bare web app and Tauri, if a thin native window (without a systray) is wanted without adding a second language. ([pywebview](https://github.com/r0x0r/pywebview))

### Form factor — summary

| Dimension | Web app (FastAPI + JS, PWA-installed) | Electron | Tauri 2.0 |
|---|---|---|---|
| Dev effort (Python backend already built) | Lowest — no extra language, no packaging step | Medium — mature tooling, but a real second stack | Medium-high — Rust shell + sidecar pattern for the Python backend |
| Packaging/distribution | None — nothing to "ship" | Real — code signing, update server | Real but lighter — WebView2 usually already on Win11 |
| Resource overhead | Lowest | ~150–300MB RAM/~80–200MB disk baseline for the shell alone | ~30–50MB RAM/2–10MB disk baseline (multiple migrations) |
| "Feels like a shipped product" ceiling | Medium-high with PWA install + `pystray` | Highest achieved-in-practice — what Claude/Cursor/ChatGPT/Windsurf use | High and rising — Jan.ai matches Electron's polish at a fraction of the cost |

## Recommendation

**Revised 2026-07-27**, superseding the initial Chainlit-first call below, after a deep-dive into CopilotKit/AG-UI's Python integration, maturity, and canvas support, prompted by clarifying what "assistant" actually means for axiom: voice-first, no browsable session list (history comes from M3 memory recall, not a thread log), and Claude-Code-level bespoke polish — not a generic multi-thread chatbot.

**Frontend: CopilotKit + AG-UI**, not Chainlit. The deciding factor is structural, not feature-count: Chainlit ships a *complete pre-built app* you configure/theme/escape-hatch out of, and its default shape is a thread/session-list app with no documented way to turn that off — reaching axiom's actual target still means using Chainlit's `custom_build` escape hatch to write a custom frontend. CopilotKit ships *hooks and components* (`useCopilotAction`, `useFrontendTool`, generative-UI primitives) with no default app shell to fight — the "no sessions" vision is simply what you get by never building a thread switcher, not a workaround. Once both paths converge on "write a custom frontend," CopilotKit wins on the features that custom frontend actually needs: a first-party, documented **Generative UI "Chat+" canvas** (the Claude-Artifacts/ChatGPT-Canvas pattern Chainlit's maintainers explicitly closed as not-planned), a real Python integration path with **no LangGraph requirement** (`copilotkit`'s `CopilotKitRemoteEndpoint`/`Action`/`add_fastapi_endpoint`, confirmed via a working code sample — or the lower-level, fully framework-agnostic `ag-ui-protocol` package for hand-emitting events directly from the PRAO loop), and a **documented precedent for a custom non-LangGraph Python agent loop** (the Pydantic AI integration) proving the exact "bespoke Python agent talks to CopilotKit via named tool-approval matching" pattern axiom would need. Backing is also simply stronger: $27M Series A (May 2026), production use at DocuSign/S&P Global/Cisco/Deutsche Telekom, both `CopilotKit` and `ag-ui-protocol` repos committed the same day as this research.

The honest cost: axiom would be writing the **entire frontend shell** (chat pane, canvas pane, voice control, approval UI) in React/Next.js from square one — CopilotKit gives you the hard, agent-specific primitives, not a finished app the way Chainlit's default UI is. HITL wiring for a custom backend is real and working but manual (name-matched tool registration, not framework auto-detection — confirmed via the Pydantic AI precedent and a maintainer-acknowledged limitation for non-Microsoft-Agent-Framework backends). Voice is documented as supported but not verified to the same code-sample depth as Chainlit's concrete `on_audio_chunk`/Realtime-API example — worth a small confirming spike before committing, not a blocker.

**Chainlit remains the fallback** if, once M10's `requirement.md` is scoped in detail, the no-session/canvas requirements turn out lighter-weight than they look today (e.g. if a simple hidden/CSS-suppressed sidebar and a `CustomElement`-based pseudo-canvas prove good enough) — its light-medium effort and native voice support are real advantages if the full custom-frontend cost of CopilotKit isn't justified by the actual feature bar. **AnythingLLM, LibreChat, and Lobe Chat remain ruled out** for the reasons in Part 1 above — none of that changes with this revision.

**Form factor: self-hosted web app first**, installed as a PWA with a `pystray` launcher for background/tray presence — **not** Electron, and not Tauri yet. This conclusion is unchanged by the frontend revision above (CopilotKit is a React SDK either way — it composes into a Next.js web app same as a Chainlit-based one would). The dev-effort math strongly favors this for a solo developer: every option needs a web frontend regardless, so skipping the native-shell wrapper is strictly less work, and Open WebUI is direct proof the resulting UX ceiling is high enough to read as "commercial." Electron's real selling point — matching what Claude Desktop/Cursor/ChatGPT ship — is bought with ~150–300MB baseline RAM and code-signing/update-server complexity that only pays off supporting many users on machines you don't control; Anthropic's own stated reasoning for staying on Electron (cross-team code-sharing, avoiding tripled maintenance) doesn't apply to a single developer running one instance on their own LAN/DGX Spark. **Tauri is the correct upgrade path later**, not now — axiom's backend already runs as a separate network service (not embedded in a UI process), which is exactly the clean separation Fluxzy's migration identifies as the precondition for a low-pain Tauri adoption, and its sidecar mechanism is a documented pattern for bundling a PyInstaller-frozen FastAPI server. Reach for it once the web UI is proven and native notifications/deeper OS integration/offline polish are actually wanted.

<summary>Original recommendation (2026-07-27, superseded above — kept for the record)</summary>

**Frontend: Chainlit**, not a generic chat-UI fork. It's the only candidate where all of streaming, blocking human-in-the-loop approval, and a native trace-view analog are direct, documented primitives rather than workarounds — and it's Python-native end-to-end, so axiom's existing PRAO loop functions become `@cl.on_message`/`@cl.step` handlers directly, with no OpenAI-compatible SSE shim (Open WebUI/LibreChat/Lobe Chat) and no cross-language control inversion (AnythingLLM's Node skill runtime). Its smaller community (12.3k★, slower commit cadence than the other four) is a real tradeoff, not a blocker, for a single-user tool. If community size/momentum is weighted more heavily than architectural fit, **AnythingLLM** is the strongest fallback — comparable approval primitive, much larger scale — at the cost of routing axiom's control loop through a Node.js skill boundary and losing token-level streaming on tool-invoking turns specifically. **Avoid LibreChat and Lobe Chat** for this specific need: LibreChat's exact hardest requirement is an acknowledged, unimplemented backlog item with no hook point, and Lobe Chat combines the heaviest integration surface with an unconfirmed gap on that same requirement and a license that restricts derivative redistribution.

This assumed a standard chat-UI shape; it did not yet account for the no-session/voice-assistant/canvas requirements clarified afterward, which is why it's superseded above rather than left standing.

</details>

## Relevance to This Project

- **Directly answers the two questions this research was launched to resolve** (raised in `.claude/plans/dryrun-plan-2.md`'s M10 discussion), as revised after the CopilotKit/AG-UI deep-dive: reuse CopilotKit's agent-UI primitives (not a generic pre-built chat-UI fork) rather than build the streaming/HITL/canvas machinery from scratch; ship as a self-hosted web app (not TUI, not Electron) for the M10 milestone.
- **Maps cleanly onto axiom's already-built milestones** — a name-matched `useFrontendTool`/action is the rendering surface for M4's Guardrails GATE approval prompts (currently a bare stdin prompt in `cli.py`); AG-UI's event stream (hand-emitted from the PRAO loop, same pattern as M2's existing JSONL trace emission) is the natural carrier for a phase-span trace view; a composed provider-switcher component is the natural surface for M6/M7's claude/local/committee selection; the Generative UI canvas pane is the natural home for any structured output axiom produces (code, documents) beyond plain chat text. None of these require new axiom-core logic — per this project's package-per-component rule, this is squarely `src/axiom/interface/` work, `loop.py` untouched.
- **Feeds directly into `012-m10-interactive-cli/requirement.md`** as the next step — the open architectural questions (frontend choice, form factor, session model, canvas) that were blocking a confident requirement.md are now resolved with cited rationale, not guessed.
- **Consistent with this project's Coding Principles** ("Reuse before build... present with recommendations. Only build custom if nothing fits") — CopilotKit's primitives fit the hard, agent-specific problems (streaming, HITL, canvas); axiom still builds its own frontend shell on top, which is the honest cost of this path, not a violation of "reuse before build" (there is no pre-built app that fits axiom's actual no-session/voice/canvas shape without an equivalent custom-frontend cost — confirmed against Chainlit specifically, not assumed).
